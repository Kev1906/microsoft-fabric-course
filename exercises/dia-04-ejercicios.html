Construye, rompe, observa y defiende.

No vas a rellenar un ticket. Vas a construir el batch de ventas de RetailOps 360, provocar fallos y decidir qué debe pasar a las 3 a.m. cuando algo no llega.

  • Parametrizar un pipeline que sirva para varios días, no para uno.
  • Diseñar fallos visibles: contexto, evidencia y contención.
  • Separar retry de idempotencia antes de tocar producción.
  • Explicar tus decisiones como si estuvieras en una entrevista senior.

Cómo trabajar

1. Lee el contexto y escribe tu respuesta sin mirar la solución. 2. Ejecuta en tu tenant de práctica; no uses datos de empleadores.

3. Documenta evidencia: run ID, filas, errores, tabla. 4. Al final, compara con la rúbrica y anota una decisión que cambiarías.

Regla: si no puedes explicar por qué tomaste una decisión, todavía no la dominas.

01

El primer vuelo de RetailOps

1 Guiada · pipeline base
30–40 min Dificultad 1/3 Individual

Contexto

Martes, 09:20. Diego quiere el primer batch de ventas funcionando antes de la demo del viernes.

De: Diego · VP de Ingeniería de Datos 09:20

Asunto: Primer batch de RetailOps

Necesito que el viernes podamos cargar ventas de dos días distintos con el mismo pipeline. No quiero un copy hardcodeado que se rompa el lunes. Deja evidencia de que funciona y de que falla con contexto cuando el archivo no está.

Lo que necesito de ti

  1. Construye pl_ingest_batch con parámetros de fecha, archivo y tabla destino.
  2. Copia un CSV de ventas a bronze.sales_raw con mapping revisado.
  3. Ejecuta con dos fechas diferentes y demuestra que la ruta dinámica cambia.
  4. Configura un guard que falle si el copy devuelve cero filas.
  5. Documenta la evidencia: parámetros, run ID, filas copiadas y resultado.
Entregable Pipeline funcionando + tabla con dos ejecuciones (una por fecha) + una nota de 5 líneas explicando por qué Overwrite es aceptable en este laboratorio y qué cambiarías en el Día 5.

Restricciones

  • No hardcodees la fecha ni el nombre del archivo en la actividad.
  • No uses Append para este ejercicio.
  • No dejes el modo de escritura sin justificar.
Pista 1: contrato
Empieza por la tabla de parámetros. Si no puedes explicar qué entra al run, todavía no puedes construir el pipeline.
Pista 2: evidencia
El run history guarda más que “falló”. Busca parámetros, output de la Copy activity y filas copiadas.
02

El archivo que no llegó

2 Independiente · fallo controlado
30–40 min Dificultad 2/3 Individual

Contexto

Jueves, 02:55. El proveedor de archivos avisa que el envío puede retrasarse.

#data-alerts 02:55

Ana: el archivo de ventas a veces llega a las 03:05 y el pipeline arranca a las 03:00. Si no está, el copy falla y nos enteramos a las 7. Necesito que el pipeline lo detecte antes y deje un error útil, no un timeout genérico.

Lo que necesito de ti

  1. Diseña una verificación previa de existencia del archivo antes del copy. Puedes usar una actividad de metadatos o una comprobación equivalente.
  2. Si el archivo no existe, falla con un mensaje que incluya fecha, ruta y una acción sugerida.
  3. Si el archivo sí existe, continúa con el copy y el guard de filas.
  4. Decide qué errores merecen retry y cuáles no. Escribe la justificación.
  5. Prueba ambos caminos: archivo presente y archivo ausente. Guarda evidencia.
Entregable Pipeline con pre-check + dos runs documentados (presente/ausente) + tabla de política de retry: error, ¿retry?, por qué.

Restricciones

  • No reintentes un error de configuración o permisos.
  • No uses un mensaje genérico como “falló el pipeline”.
  • No asumas que el archivo existe porque “ayer existió”.
Pista 1: antes del copy
¿Qué actividad puede decirte si un archivo o carpeta existe sin moverlo? Piensa en metadatos, no en otra copia.
Pista 2: mensaje útil
Un guard de guardia necesita saber qué archivo, qué partición y qué run. Incluye esos tres datos en el error.
03

El batch de las 3 a.m.

3 Senior · incidente y diseño
45–60 min Dificultad 3/3 Equipo

Contexto

Lunes, 08:30. El batch nocturno falló, alguien lo re-ejecutó y ahora hay más filas que ayer.

De: Marta · Analytics Lead 08:30

Asunto: El stock está mal y el batch duplicó ventas

El pipeline falló a las 3:07. Alguien lo volvió a ejecutar a las 5:00 y ahora bronze.sales_raw tiene unas 12.000 filas de más. Tres tiendas muestran stock incorrecto. Necesito saber qué pasó, cómo evitar que se repita y cómo re-ejecutar sin miedo.

#data-alerts 08:42

Diego: y quiero saber si esto se puede detectar antes de que lo vea operaciones. No quiero otra reunión donde digamos “añadiremos un test”.

Lo que necesito de ti

  1. Reconstruye el incidente: línea de tiempo, causa raíz y por qué el reintento duplicó.
  2. Diseña el batch operable: qué actividades, parámetros, dependencias y write mode usarías para que re-ejecutar sea seguro. Puedes separar ingesta y publicación.
  3. Contención y alerta: qué hace el pipeline cuando falla, qué evidencia deja y cómo se entera el equipo antes de las 7.
  4. Costo y escala: qué cambiarías si el volumen crece 10x o si el archivo llega tres horas tarde.
  5. Runbook: pasos exactos para recuperar, validar y comunicar.
Entregable Tabla de incidente (síntoma, causa, evidencia), diagrama del pipeline objetivo, ADR de write mode, runbook de recuperación y tres métricas que demostrarían que el problema no vuelve.

Restricciones

  • No propongas “revisar mejor” ni “añadir un test” sin decir qué se comprueba y qué bloquea.
  • No asumas que el retry es seguro: justifica la idempotencia.
  • No diseñes un monolito de 100 actividades; usa parent/child si aporta.
  • No ocultes el trade-off de costo o latencia.
Pista 1: la duplicación no es un bug del copy
Si la escritura es Append y el run se repite, el resultado es el esperado por el diseño. El problema está en la decisión de write mode y en la clave de idempotencia.
Pista 2: separa ingesta de publicación
Una tabla staging o un batch_id puede permitir cargar, validar y publicar de forma atómica. No todo tiene que escribirse directo en la tabla que consume el negocio.
