La solución no es el pipeline. Es el criterio con el que lo diseñas.

Hay muchas formas válidas de resolver estas misiones. Lo que separa una respuesta junior de una Staff no es la cantidad de actividades: es el contrato, la contención, la evidencia y la decisión explícita sobre re-ejecución.

Cómo leer esta página

No copies. Compara. Pregúntate qué riesgo viste tú que aquí falta y qué supuesto tuyo no sobreviviría a un archivo tardío o a un reintento.

Calibra. La rúbrica es 0–3 por criterio. Un 2 sólido es bueno; no necesitas 3 en todo para avanzar.

Anota. Guarda una decisión que cambiarías después de leer. Ese es el aprendizaje real.

01

Cómo aborda esto un Staff Engineer

Antes de las respuestas concretas, este es el orden mental que uso. Sirve para cualquier pipeline de RetailOps, no solo para el Día 4.

  1. 1 Define el contrato Qué entra, qué sale, qué fecha, qué archivo, qué tabla y quién puede ejecutarlo. Si el contrato es borroso, el pipeline será frágil.
  2. 2 Diseña la contención Qué pasa si el archivo no llega, si el copy falla, si no hay filas o si el reintento se ejecuta dos veces. La ruta de fallo no arregla; contiene y hace visible.
  3. 3 Deja evidencia Run ID, parámetros, filas, output, error y resultado. Sin evidencia no hay operación, solo fe.
  4. 4 Piensa en la re-ejecución El botón Run debe ser seguro o debe estar protegido. Append ciego es una fábrica de duplicados.
  5. 5 Nombra el trade-off Overwrite vs merge, retry vs fail fast, pipeline vs notebook, staging vs directo. Toda decisión cuesta.
02

Misión 01 · El primer vuelo de RetailOps

Cómo lo abordaría

Primero escribo el contrato de parámetros, no la actividad. Si no sé qué fecha, archivo y tabla recibe el run, no puedo probar dos fechas ni defender el diseño. Después construyo el camino feliz y, por último, el guard de filas y la evidencia.

Parámetro Ejemplo Por qué importa
p_process_date 2026-11-20 Define la partición lógica y la ruta del archivo.
p_source_file sales.csv Permite cambiar el nombre sin editar la actividad.
p_target_table bronze.sales_raw Permite probar una tabla staging antes de publicar.

Una respuesta sólida

Contrato del pipeline 
pipeline pl_ingest_batch(p_process_date, p_source_file, p_target_table)

  Set batch id:
    var_batch_id = @guid()

  Copy sales:
    source = @concat(
      'Files/landing/sales/',
      pipeline().parameters.p_process_date,
      '/',
      pipeline().parameters.p_source_file
    )
    destination = @pipeline().parameters.p_target_table
    write_mode = overwrite
    retry = 2, interval = 30s, timeout = 30m

  Rows copied?:
    @greater(activity('Copy sales').output.rowsCopied, 0)

  True  -> Set var_load_status = 'success'
  False -> Fail NO_ROWS with file + date + run id

Evidencia de las dos ejecuciones

Run p_process_date p_source_file Filas Resultado
1 2026-11-20 sales.csv 5.000 Éxito, tabla reemplazada.
2 2026-11-21 sales_2026-11-21.csv 5.120 Éxito, ruta dinámica distinta.
3 2026-11-22 no_existe.csv — Fallo controlado con contexto.
★

Por qué Overwrite es aceptable aquí

Porque el lote es pequeño, la tabla es bronze y el objetivo es demostrar un run repetible. No es la respuesta para un histórico de 10 GB: reescribir todo cada día sería caro. En el Día 5 pasas a incremental con watermark y merge; esa es la evolución natural, no un fracaso del Día 4.

Lo que no haría

  • Hardcodear la fecha y el archivo en la actividad.
  • Usar Append “porque es más rápido” y luego re-ejecutar.
  • Declarar éxito con cero filas copiadas.
  • Entregar una captura de pantalla sin run ID, parámetros ni filas.
i

Señales de un 3/3 en esta misión

El pipeline corre con dos fechas distintas, el guard de filas existe, la ruta de fallo deja contexto y la nota explica el trade-off de Overwrite con una alternativa para el Día 5.

03

Misión 02 · El archivo que no llegó

Cómo lo abordaría

El fallo no es “el copy falló”. El fallo es “el archivo no está y el pipeline no lo dijo con claridad”. Antes de copiar, verifico la existencia y convierto la ausencia en un error de negocio explícito. Después decido qué errores merecen retry y cuáles no.

Camino de verificación

Get metadataexiste el archivo
If Conditionexists = true
Copy salescontinuar
Fail FILE_NOT_FOUNDfecha + ruta + run
!

Verifica el output de tu conector

La actividad de metadatos expone campos como existencia, tipo y tamaño, pero el nombre exacto depende del conector. Abre el output real del run antes de construir la condición. No confíes en una captura de otro tenant.

Política de retry

Error ¿Retry? Por qué
Timeout de red Sí, acotado Puede ser transitorio; no quiere decir que el archivo esté mal.
429 / throttling Sí, con backoff El servicio está limitando; esperar puede resolverlo.
Archivo inexistente No Reintentar no lo crea. Falla con contexto y escala.
Credencial inválida No Es un problema de identidad; reintentar solo retrasa el fallo.
Esquema incompatible No Necesita intervención o cuarentena, no más intentos.

Una respuesta sólida

El pipeline comprueba la existencia antes del copy. Si no existe, falla con un mensaje como:

Mensaje de negocio 
FILE_NOT_FOUND | date=2026-11-21 |
path=Files/landing/sales/2026-11-21/sales.csv |
action=confirmar si el proveedor envió el archivo |
run=@pipeline().RunId

Si el archivo existe, el copy sigue y el guard de filas se mantiene. El retry se configura solo para errores transitorios; el archivo ausente falla rápido.

Trade-off

La verificación previa añade una actividad y un pequeño costo. A cambio, convierte un fallo ambiguo en un error de negocio claro. Si el archivo llega siempre y el copy ya falla con buen contexto, podrías omitirla; pero en RetailOps el archivo es la frontera con un proveedor y merece un contrato explícito.

Lo que no haría

  • Reintentar la ausencia del archivo tres veces.
  • Usar un mensaje genérico que no diga qué archivo ni qué partición.
  • Confundir “archivo existe” con “archivo tiene datos válidos”: el guard de filas sigue siendo necesario.
04

Misión 03 · El batch de las 3 a.m.

Reconstrucción del incidente

Hora Qué pasó Evidencia que faltaba
03:00 Arranca pl_ingest_batch. Parámetros del run y batch_id.
03:05 El archivo del proveedor aún no llega. Chequeo de existencia o freshness.
03:07 El copy falla por timeout; no hay retry ni failure path. Error con archivo, fecha y run; notificación.
05:00 Alguien re-ejecuta manualmente sobre una tabla con Append. Política de re-ejecución idempotente y clave única.
07:00 El dashboard muestra duplicados y stock incorrecto. Validación de volumen/reconciliación post-carga.
08:30 Analytics escala el incidente. Alerta proactiva y runbook.

Causa raíz: el write mode era Append y el pipeline no tenía una clave de idempotencia. El reintento manual no fue “un error humano”: fue la consecuencia predecible de un diseño que permitía duplicar. La falta de alerta solo hizo que se descubriera más tarde.

Diseño objetivo

Orquestación

pl_orchestrateparent
pl_ingest_batchstaging + batch_id
pl_publish_salesvalidar + merge
Post-validaciónvolumen + freshness
↓

Contención y evidencia

Failure patherror con contexto
Alertascheduled + monitoring
Runbookrecuperar sin duplicar
Métricasduplicados, volumen, MTTR
Decisión Alternativa Por qué la elegiría Consecuencia
Staging + MERGE por clave Append directo Re-ejecutar es idempotente; el negocio no ve filas a medias. Más compute y una tabla staging que mantener.
Parent/child Monolito de 100 actividades Ingesta y publicación tienen contratos y fallos separados. Más items y una capa de orquestación que documentar.
Alerta proactiva Solo run history El equipo se entera antes de las 7, no después. Requiere monitoring/Activator y un dueño de la alerta.
Retry acotado Retry infinito Contiene fallos transitorios sin amplificar duplicados. Puede dejar un fallo permanente sin escalar si no hay ruta de fallo.

ADR de ejemplo

Decisión Cargar a staging y publicar con MERGE por sale_id, usando batch_id para trazabilidad.
Alternativas Append directo; overwrite completo; deduplicación posterior en gold.
Por qué El negocio consume bronze y no puede ver filas duplicadas ni lotes a medias. La re-ejecución debe ser segura.
Consecuencia Más costo de compute y una tabla staging; se compensa con menos incidentes y reprocesos.

Runbook de recuperación

  1. Detectar: alerta de fallo o volumen anómalo; identificar batch, fecha y archivo.
  2. Contener: no re-ejecutar con Append; pausar la publicación si el lote está incompleto.
  3. Validar: contar filas, revisar claves duplicadas y comparar contra la línea base.
  4. Recuperar: reprocesar el mismo batch con MERGE; si hubo corrupción, restaurar o reprocesar desde la fuente.
  5. Comunicar: estado, impacto, siguiente actualización y hora estimada.
  6. Aprender: postmortem sin culpables; añadir el control que faltó y probarlo.

Métricas que demostrarían que no vuelve

  • Duplicate rate en bronze por lote (objetivo 0).
  • Detección: tiempo entre fallo y alerta (objetivo < 10 min).
  • Recovery time: tiempo entre detección y batch validado (objetivo < 1 h).
  • Row count vs baseline: desviación fuera de rango que bloquea publicación.

Lo que no haría

  • Decir “reintentamos y salió” sin comprobar duplicados.
  • Poner un test manual que nadie ejecuta.
  • Asumir que el proveedor siempre llegará a tiempo.
  • Diseñar un monolito que combine ingesta, transformación y publicación.
05

Rúbrica senior

Seis criterios, 0–3 cada uno. El curso considera aprobado un promedio ≥ 2,5 y ningún criterio en 0. No es una nota escolar: es una calibración para saber qué reforzar antes del Día 5.

CriterioPuntosQué mira un Staff
Corrección técnica0–3El pipeline corre, los parámetros se usan, el mapping es correcto y el guard de filas funciona.
Trade-offs0–3Compara Overwrite/Append/Merge, retry/fail-fast y pipeline/notebook con consecuencias, no eslóganes.
Operación0–3Failure path, timeout, retry, evidencia y runbook. Sabe qué hacer a las 3 a.m.
Costo y performance0–3Reconoce CUs, reintentos, copias completas y el costo de staging/merge.
Seguridad y gobierno0–3No mete secretos en parámetros, piensa en identidades y en el blast radius del dato.
Comunicación0–3Explica el diseño en 90 segundos, con contexto, decisión, trade-off y métrica.
2.5–3.0 Staff: operable y defendible. Ningún criterio en 0.
2.0–2.4 Sólido: funciona, pero falta un trade-off o una métrica.
1.0–1.9 Junior: el camino feliz funciona; la operación queda para después.
0–0.9 Rehacer: no hay contrato, evidencia ni contención.

Qué mide cada misión

Misión Foco principal Señal de 3/3
01 · Primer vuelo Corrección, parámetros, evidencia. Dos fechas distintas, guard de filas y nota de Overwrite con evolución.
02 · Archivo ausente Contención, retry, mensaje de negocio. Pre-check, error con fecha/ruta/run y política de retry justificada.
03 · Batch de las 3 a.m. Idempotencia, operación, costo, comunicación. Staging + merge, parent/child, alerta, runbook y métricas.
★

Las cinco señales de una respuesta Staff

1) Contrato explícito. 2) Fallo contenido y visible. 3) Evidencia reproducible. 4) Re-ejecución segura o bloqueada. 5) Trade-off con costo, latencia o cobertura. Si falta una, todavía hay margen.

06

Qué sigue

El Día 5 convierte el copy en una carga incremental real: watermark, CDC, duplicados, idempotencia y conectividad. Llega con el pipeline funcionando y con una lista de dudas; no con una captura sin contexto.
