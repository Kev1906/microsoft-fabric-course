Un pipeline no mueve datos. Decide qué pasa cuando algo falla.

Hoy conviertes Data Factory en el plano de control de RetailOps 360: actividades, parámetros, expresiones, dependencias, reintentos y rutas de fallo. El objetivo no es que el copy funcione una vez, sino que el batch sea operable a las 3 a.m.

00

Recuperación activa: lo que ya debes tener

Días 1–3 te dieron el mapa de Fabric. Antes de abrir Data Factory, comprueba que el mapa sigue en tu cabeza. Responde sin mirar apuntes; después abre la respuesta.

5 preguntas · 10 minutos

1. ¿Cuál es la relación entre tenant, capacity, workspace e item?

Un tenant contiene una o más capacities. Cada capacity aporta compute (CUs) y contiene workspaces. Cada workspace contiene items (lakehouse, warehouse, notebook, pipeline…). El dato vive en OneLake; el item es la puerta de acceso y el workspace es el contenedor de colaboración.

2. ¿Cuándo un shortcut es mejor que copiar datos?

Cuando quieres una referencia viva al dato sin duplicarlo, y el equipo dueño mantiene el control de acceso. Copiar tiene sentido cuando necesitas aislamiento, una transformación física o un snapshot estable. Shortcut no es gratis: hereda dependencias de red, permisos y latencia del origen.

3. ¿Qué diferencia hay entre un workspace role y un dominio?

El workspace role es control de acceso: Admin, Member, Contributor o Viewer. El dominio es una agrupación lógica para gobierno y descubrimiento; no reemplaza los permisos del workspace. Un dominio ordena; un rol autoriza.

4. ¿Qué significa que una capacity esté throttled?

Que el consumo superó el presupuesto disponible y Fabric empieza a limitar operaciones. Las interacciones pueden retrasarse o rechazarse y algunos trabajos en background pueden esperar o fallar. No es “un bug del pipeline”: es economía de capacidad. Día 21 lo profundiza.

5. ¿Por qué un pipeline de Fabric necesita una capacity?

Porque ejecutar actividades consume CUs de la capacity a la que está asignado el workspace. El pipeline no “vive” en el aire: su workspace debe estar respaldado por una capacity F o Trial. Un workspace Pro no habilita items no-Power BI como pipelines.

★

01

03:07 a.m.: el batch que “no cargó”

El pipeline pl_ingest_batch corre todas las noches a las 03:00. A las 03:05 llega el archivo de ventas del día a OneLake. La Copy activity falla por un timeout de red. No hay reintento. No hay ruta de fallo. No hay alerta. A las 07:00, el dashboard de tiendas muestra el día anterior.

El analista de guardia escribe en Slack: “Fabric no cargó los datos”. El CTO pregunta si el problema es la plataforma. Y el equipo empieza a buscar en el lugar equivocado: revisa el archivo, la conexión, el lakehouse… cuando el verdadero problema es que el pipeline no tenía un plan para el fallo.

◆

Lo que un senior ve

El copy falló. Eso puede pasar. Lo que no puede pasar es que el fallo sea silencioso, que no haya evidencia y que nadie sepa si el batch se puede reintentar sin duplicar datos. Un pipeline no es un notebook con flechas: es un contrato operativo.

Antes de leer la teoría

¿Qué habrías configurado para que este incidente se detectara y se contuviera?

Ver las cuatro decisiones mínimas
  1. Retry para errores transitorios de red, con un número limitado y un intervalo razonable.
  2. Failure path a una actividad que falle con contexto o notifique; no dejar que el copy “desaparezca”.
  3. Guard de filas: si el copy devuelve cero filas, el pipeline no debe declarar éxito.
  4. Parámetros y runbook: fecha, archivo y tabla destino explícitos; saber cómo re-ejecutar sin duplicar.

Fíjate: ninguno de los cuatro es “escribir mejor SQL”. Son decisiones de orquestación. Ese es el tema de hoy.

02

El modelo mental: el director de orquesta

Imagina una orquesta. El director no toca el violín ni el piano. Decide quién entra, cuándo, con qué intensidad y qué hace la orquesta si un músico se pierde. Un pipeline de Fabric es ese director: no transforma los datos, coordina a quien los transforma.

En la orquesta En Fabric Qué decide
Director Pipeline Orden, dependencias, parámetros, reintentos y rutas de fallo.
Músicos Actividades Copy, notebook, dataflow, stored procedure, Fail, Wait…
Solista Notebook / Spark Transformación compleja, estado, lógica de negocio y tests.
Partitura Parámetros y expresiones Qué fecha, qué archivo, qué tabla y qué configuración usa este run.
Señales Dependencias Qué corre en éxito, en fallo, al completar o al saltarse.
Plan de emergencia Failure path + retry Cómo se contiene el fallo y cómo se recupera el servicio.
i

Si solo te llevas una idea

El pipeline es plano de control; el notebook es plano de cómputo. Mantén la orquestación delgada y pon la lógica de negocio donde se pueda probar: un notebook, SQL o un job de Spark. Cuando mezclas las dos capas, terminas con un pipeline imposible de depurar.

Pipeline como notebook

  • Cien actividades que intentan transformar fila a fila.
  • Expresiones gigantes con reglas de negocio escondidas.
  • Nadie sabe qué hace el pipeline sin abrir cada nodo.
  • El fallo se diagnostica “probando cosas”.

Pipeline como orquestador

  • Pocas actividades con nombres claros.
  • La lógica vive en notebooks, SQL o dataflows versionables.
  • El pipeline aporta orden, parámetros y manejo de fallos.
  • El run history cuenta una historia legible.

Predice

Un pipeline copia un archivo y luego ejecuta un notebook. ¿Dónde debería vivir la regla “si el margen es negativo, marcar la fila como sospechosa”?

Ver respuesta
En el notebook o en SQL

No en una expresión del pipeline. La regla necesita tests, versionado y datos para probarse. El pipeline solo debe decidir cuándo se ejecuta el notebook y qué hacer si falla.

03

Anatomía de un pipeline de Fabric

Un pipeline se compone de actividades conectadas por dependencias. Las actividades se agrupan en tres familias. No necesitas memorizar el catálogo completo; necesitas saber qué familia resuelve qué problema.

Movimiento

Mueven datos

Copy activity y Copy job. Conectan origen y destino, mapean columnas y escriben en lakehouse, warehouse u otro sistema.

Transformación

Procesan datos

Notebook, Dataflow Gen2, Spark job definition, stored procedure, SQL script. Aquí vive la lógica que cambia el dato.

Control

Deciden el flujo

If Condition, ForEach, Switch, Until, Wait, Fail, Set variable, Invoke pipeline. No mueven datos: gobiernan el run.

En este día construimos un pipeline de ingesta. El patrón mínimo sano es: parámetros → preparación → movimiento → validación → éxito o fallo explícito. En el camino aprendes las piezas que usarás en todos los días siguientes.

Pieza Pregunta que responde En pl_ingest_batch
Parámetros ¿Qué valores externos recibe este run? Fecha, archivo, tabla destino.
Variables ¿Qué estado interno necesito recordar? var_batch_id, var_load_status.
Actividades ¿Qué trabajo concreto se ejecuta? Copy sales, If Condition, Fail.
Dependencias ¿Qué corre después de qué? Éxito → validar filas; fallo → contener.
Trigger ¿Cuándo empieza el run? Manual hoy; schedule o evento después.
Run history ¿Qué pasó, cuándo y con qué parámetros? Evidencia para operar y depurar.

04

Parámetros, variables y expresiones

Un pipeline bueno se escribe una vez y se ejecuta muchas veces con valores distintos. Para eso necesitas separar tres cosas que suenan parecidas pero no lo son.

Parámetro

Entra y no cambia

Valor externo definido al inicio del run. Tiene tipo y valor por defecto. Se referencia como @pipeline().parameters.nombre.

Variable

Cambia durante el run

Estado interno que puedes setear o modificar con actividades. Sirve para acumular, marcar estado o pasar información entre pasos.

Sistema

La provee Fabric

pipeline().RunId, pipeline().TriggerTime, entre otros. Son de solo lectura y sirven para trazabilidad.

La sintaxis que sí necesitas

Una expresión empieza con @. Si aparece dentro de un string, se usa @{...} y el resultado siempre es string. Las funciones se combinan: concat, utcnow, formatDateTime, guid, greater.

Expresiones de Data Factory 
-- Ruta del archivo a copiar
@concat(
  'Files/landing/sales/',
  pipeline().parameters.p_process_date,
  '/',
  pipeline().parameters.p_source_file
)

-- Fecha de hoy en formato de partición
@formatDateTime(utcnow(), 'yyyy-MM-dd')

-- Identificador único del batch
@guid()

-- Filas que devolvió la Copy activity
@activity('Copy sales').output.rowsCopied

-- Condición booleana para un If Condition
@greater(activity('Copy sales').output.rowsCopied, 0)

-- Identidad del run para trazabilidad
@pipeline().RunId
!

No metas secretos en parámetros

Los parámetros son visibles en la definición y en el historial. “Secure input/output” evita que el valor aparezca en logs, pero no es un almacén de secretos. Las credenciales viven en conexiones, identidades administradas o Key Vault; lo verás a fondo en los Días 5 y 18.

Predice el resultado

Si p_process_date = '2026-11-20' y p_source_file = 'sales.csv', ¿qué devuelve la primera expresión?

Ver resultado

Files/landing/sales/2026-11-20/sales.csv

La expresión completa devuelve un string. Si usaras @{...} dentro de un texto más largo, también sería string; si usas @pipeline().parameters.p_quantity sin interpolación y el parámetro es numérico, conserva el tipo.

★

Regla de senior

Parametriza lo que cambia entre runs: fecha, archivo, tabla, lote, región. No parametrices todo por deporte. Cada parámetro es un contrato que alguien tendrá que llenar y depurar a las 3 a.m.

05

Dependencias: el pipeline como grafo, no como lista

Las actividades se conectan con dependencias. La condición de la dependencia decide si la actividad siguiente corre. Esto es lo que convierte un pipeline en un sistema operable y no en una cadena de clics.

Condición Cuándo corre Uso típico Riesgo si la usas mal
On success La actividad previa terminó bien. Continuar el flujo normal. Asumir que “bien” significa “datos correctos”.
On failure La actividad previa falló. Contener, notificar, registrar contexto. Creer que la ruta de fallo arregla la causa.
On completion Terminó, con éxito o fallo. Auditoría, limpieza, métricas. Poner lógica de negocio aquí: corre incluso si falló.
On skip La actividad previa fue desactivada. Manejo de ramas desactivadas en desarrollo. Olvidar que una actividad inactiva no produce output.

i

La frase que separa junior de senior

La ruta de fallo no arregla el fallo: lo hace visible y contenido. Arreglar la causa es otra conversación: reintentar, corregir el archivo, reprocesar o escalar. El pipeline solo debe dejar claro qué pasó y qué se puede hacer después.

Diseño de dependencias

Si la Copy activity falla, ¿qué actividades podrían ejecutarse según las condiciones que conectaste?

Ver respuesta

Las conectadas con On failure y las conectadas con On completion. Si conectas un notebook al “completion”, se ejecutará aunque el copy haya fallado. Por eso el completion es para auditoría o limpieza, no para transformar datos que asumen éxito.

06

Reintentos, timeout y rutas de fallo

Un fallo no es una sola cosa. Hay fallos transitorios que merecen un reintento y fallos permanentes que solo empeoran si los repites. La configuración de retry es una decisión de riesgo, no un checkbox.

Configuración Valor por defecto / límite Qué significa
Timeout 12 h por defecto; máximo 7 días. Cuánto puede correr una actividad antes de fallar por tiempo.
Enable retries Apagado por defecto. Activa reintentos automáticos para fallos transitorios.
Retry count 1 por defecto. Cuántas veces se intenta de nuevo antes de marcar fallo.
Retry interval 30 s por defecto. Espera entre intentos. Puede ser fija o con increasing delay.
Retry conditions Preview. Reintentar solo ciertos errores (por ejemplo, código 429) en lugar de cualquier fallo.

Transitorio: reintenta

  • Timeout de red o throttling temporal.
  • Servicio momentáneamente no disponible.
  • Error 429 con backoff.
  • Fallo intermitente del conector.

Permanente: falla rápido

  • Credencial inválida o permiso insuficiente.
  • Archivo inexistente o esquema incompatible.
  • Error de expresión o parámetro mal tipado.
  • Regla de negocio incumplida.
!

Retry no es idempotencia

Si tu Copy activity escribe con Append y falla a mitad, un reintento puede duplicar filas. El retry no te salva de un diseño no idempotente. En el Día 5 verás incremental, watermark y merge; hoy, para el laboratorio, usaremos Overwrite para que re-ejecutar sea seguro dentro de un lote pequeño.

Notificaciones: lo que sí y lo que no

En Fabric puedes configurar notificaciones de fallo para runs programados. En runs bajo demanda, esa notificación no se envía. Si necesitas alertas más ricas, el camino es monitoring/workspace monitoring + Activator (Día 20). No confundas “hay un correo” con “hay observabilidad”.

Decide el comportamiento

Un pipeline falla porque el service principal perdió permisos. ¿Reintentar tres veces con backoff es una buena idea?

Ver razonamiento
No

Es un fallo permanente para ese run. Reintentar no cambia los permisos; solo retrasa el fallo y consume capacidad. Falla rápido, deja un error claro y escala a la persona que puede corregir la identidad.

07

Pipeline, notebook, Copy job o Dataflow

DP-700 no pregunta “¿conoces el botón?”. Pregunta “¿qué herramienta elegirías y por qué?”. Esta tabla es la respuesta corta; el criterio largo se construye con los días siguientes.

Herramienta Fortaleza Úsala cuando… Evítala cuando…
Pipeline Orquestar actividades, dependencias, parámetros, retries y fallos. Necesitas coordinar copy, notebooks, SQL y notificaciones. La lógica de negocio es compleja o necesita tests unitarios.
Notebook Spark, PySpark, transformación compleja, librerías y estado. Necesitas joins, ventanas, SCD2, calidad o ML. Solo necesitas mover un archivo o coordinar pasos simples.
Copy job Movimiento simple, incluido incremental/CDC, con menos diseño. El caso es “copiar datos” y no necesitas un grafo de control. Necesitas dependencias, ramas o control fino por actividad.
Dataflow Gen2 Transformación low-code con Power Query. El equipo prefiere low-code y la transformación es acotada. Necesitas control de Spark, tests de código o lógica avanzada.

Tres formas de construir el mismo batch

Nivel 1 · frágil

Copy hardcodeado

Una Copy activity con ruta y fecha fijas, sin retry ni fallo. Funciona hoy; mañana alguien olvida cambiar la fecha y copia el archivo equivocado.

Nivel 2 · reusable

Copy parametrizado

Parámetros de fecha y archivo, retry para errores transitorios y un If Condition que falla si no hay filas. El mismo pipeline sirve para varios días.

Nivel 3 · operable

Batch con contención

Parámetros, batch_id, failure path con contexto, guard de filas, timeout, evidencia y una tabla destino segura para re-ejecutar. Esto es lo que quieres llevar a producción.

★

Cuándo NO usar un pipeline

Para transformaciones pesadas, streaming, lógica con estado complejo o procesos que necesitan tests de código, usa el motor adecuado y deja que el pipeline lo orqueste. Un pipeline con cien actividades suele ser una señal de que la lógica pertenece a otro sitio.

08

Code review: el mismo batch, dos niveles

Mira estas dos configuraciones como si fueras el reviewer. No evalúas si “funciona”: evalúas si se puede operar, depurar y volver a ejecutar sin miedo.

Junior

  • Copy activity con Files/landing/sales/2026-11-20/sales.csv hardcodeado.
  • Tabla destino bronze.sales_raw con Append.
  • Sin retry, sin timeout ajustado, sin ruta de fallo.
  • Si el archivo no existe, el pipeline falla sin contexto.
  • Si se re-ejecuta, duplica filas.

Profesional

  • Parámetros de fecha, archivo y tabla destino.
  • Retry 2 con intervalo de 30 s y timeout de 30 min.
  • Failure path a un Fail activity con contexto del archivo y la fecha.
  • If Condition falla si rowsCopied = 0.
  • Overwrite en el laboratorio; incremental/merge en el Día 5.
Contrato del pipeline · pseudocódigo 
pipeline pl_ingest_batch(
  p_process_date,
  p_source_file,
  p_target_table
):
  var_batch_id = guid()

  copy "Copy sales":
    source = Files/landing/sales/{p_process_date}/{p_source_file}
    destination = {p_target_table}
    write_mode = overwrite
    retry = 2, interval = 30s, timeout = 30m

  on success:
    if rowsCopied > 0:
      set var_load_status = "success"
    else:
      fail "NO_ROWS" with file + date context

  on failure:
    fail "COPY_FAILED" with file + date context

  evidence:
    run history, rowsCopied, batch_id, parameters

Análisis

Dimensión Junior Profesional
Reusabilidad Un pipeline por día o edición manual. Un pipeline para cualquier fecha y archivo.
Contención El fallo se descubre por el dashboard roto. El fallo termina en una actividad con contexto.
Re-ejecución Append duplica; nadie sabe si es seguro. Overwrite seguro para el lote; incremental después.
Diagnóstico “Falló el copy”. Archivo, fecha, batch y filas copiadas en el run history.
Costo Reintentos manuales y reprocesos. Retry acotado y timeout explícito.

Puntuación: Junior 2/10. Profesional 9/10. No le doy 10 porque todavía no hay incremental ni merge idempotente (Día 5), no hay promoción por entornos (Día 19) y no hay alerta operativa rica (Día 20). Un 10 no es “más YAML”: es el sistema completo.

09

Demo guiada: construye pl_ingest_batch

Esta demo está diseñada para que la ejecutes en tu tenant. La interfaz puede cambiar de nombre en algún label; si eso pasa, busca la acción equivalente y contrasta con la documentación oficial enlazada al final.

!

Antes de empezar

Workspace fabric-de-dev asignado a una capacity Trial o F. Lakehouse lh_retailops con schema bronze. Si tu lakehouse no usa schemas, el nombre de tabla será sales_raw en lugar de bronze.sales_raw.

Paso 0 · Genera y sube el archivo

Usa el generador sintético del curso o crea un CSV pequeño con las columnas del dataset. El archivo debe quedar en la ruta:

Ruta del archivo en el lakehouse 
lh_retailops / Files / landing / sales / 2026-11-20 / sales.csv

Si usas el generador del repositorio:

Terminal 
python datasets/generate_retailops.py --rows 5000 --out datasets/out
# Sube datasets/out/sales_2026-11-20.csv a la ruta de arriba

Paso 1 · Crea el pipeline

  1. 1 Nuevo item → Pipeline Nombre: pl_ingest_batch. Descripción: “Ingesta batch de ventas a bronze”. En el buscador escribe Pipeline, no “Data pipeline”.
  2. 2 Abre la pestaña Parameters Selecciona el fondo del canvas y busca la pestaña de parámetros del pipeline.
!

Si no ves “Data pipeline”, es normal

Desde septiembre de 2025 el item se llama Pipeline en la lista de workspace y en New item. Microsoft cambió solo el nombre visible: el tipo de item sigue siendo DataPipeline en la API. Si buscas “Data pipeline” y no aparece, escribe Pipeline.

Si tampoco aparece Pipeline, revisa en Workspace settings → Workspace type que el workspace esté en Fabric Trial o en una capacity F. Un workspace en Pro no habilita items de Data Factory.

Paso 2 · Define el contrato de parámetros

Parámetro Tipo Default Para qué
p_process_date String 2026-11-20 Partición lógica del batch.
p_source_file String sales.csv Nombre del archivo a copiar.
p_target_table String bronze.sales_raw Tabla destino (ajusta si no usas schemas).
★

Predice antes de ejecutar

Si p_process_date = '2026-11-21' y no existe el archivo, ¿qué camino tomará el pipeline? Escríbelo antes de correr. Después compara con el run history.

Paso 3 · Agrega la variable interna

Añade una actividad Set variable llamada Set batch id. Crea la variable var_batch_id de tipo String y asígnale:

Expresión · var_batch_id 
@guid()

Esta variable no cambia el resultado del copy; te da un identificador para correlacionar el run con la tabla de auditoría que construirás más adelante. Es una decisión de operabilidad, no de transformación.

Paso 4 · Configura la Copy activity

  1. 4 Agrega Copy data Nómbrala Copy sales. Conéctala después de Set batch id con On success.
  2. 5 Source Lakehouse → Files. Ruta dinámica: @concat('Files/landing/sales/', pipeline().parameters.p_process_date, '/', pipeline().parameters.p_source_file). Formato CSV con header.
  3. 6 Destination Lakehouse → Tables. Tabla: @pipeline().parameters.p_target_table. Table action: Overwrite para este laboratorio.
  4. 7 Mapping Importa el schema y verifica los tipos. No dejes que el copy “adivine” fechas y decimales sin revisar.
  5. 8 General Retry: 2. Intervalo: 30 s. Timeout: 30 min. Secure input/output si algún parámetro pudiera contener información sensible.

Paso 5 · Valida que haya filas

Añade un If Condition llamado Rows copied?, conéctalo desde Copy sales en On success y usa:

Expresión · condición 
@greater(activity('Copy sales').output.rowsCopied, 0)
  • True: Set variable var_load_status = 'success'.
  • False: Fail activity Fail no rows, código NO_ROWS, mensaje con fecha y archivo.
!

Output del conector

El campo exacto del output depende del conector y del tipo de datos. En copias tabulares verás rowsCopied; en otros casos puede ser rowsRead o filesWritten. Abre el output real de tu actividad y verifica antes de confiar en el guard.

Paso 6 · Ruta de fallo

Conecta Copy sales a un Fail activity llamado Fail copy usando la condición On failure. Configura un mensaje que sirva a la persona de guardia:

Expresión · mensaje de fallo 
@concat(
  'COPY_FAILED | date=', pipeline().parameters.p_process_date,
  ' | file=', pipeline().parameters.p_source_file,
  ' | run=', pipeline().RunId
)

No pongas el mensaje “falló el copy”. Eso ya lo sabía. El mensaje debe decir qué archivo, qué fecha y qué run, para que la recuperación no empiece con una investigación arqueológica.

Paso 7 · Ejecuta y observa

  1. Ejecuta con los valores por defecto y revisa el Output de cada actividad.
  2. Verifica la tabla bronze.sales_raw y el número de filas.
  3. Vuelve a ejecutar con el mismo archivo: con Overwrite no deberías duplicar.
  4. Cambia p_source_file a un nombre inexistente y observa la ruta de fallo.
  5. Cambia p_process_date a una fecha con archivo válido y confirma que la ruta dinámica funciona.
  6. Documenta el run ID, filas copiadas y resultado en tu bitácora.
i

Lo que acabas de demostrar

No demostraste que “sabes hacer clic en Copy”. Demostraste que puedes diseñar un run con contrato de parámetros, evidencia, contención y una decisión explícita sobre re-ejecución. Eso es lo que se evalúa en una entrevista senior.

10

Lo que un senior ve

El pipeline ya corre. Ahora viene la parte que casi nadie documenta: qué pasa cuando el volumen crece, cuando el archivo llega tarde, cuando el conector cambia y cuando el costo importa.

Decisión Ganas Pagas Cuándo cambias
Overwrite Re-ejecución simple y segura para un lote. Reescribes toda la tabla; no escala a histórico completo. Cuando necesitas incremental o merge (Día 5).
Append Barato y simple para eventos inmutables. Duplicados en reintentos; requiere dedup después. Cuando tienes clave única y un patrón de merge.
Copy activity Control fino dentro de un pipeline. Más configuración y más superficie de error. Cuando solo necesitas mover datos simples: Copy job.
Retry agresivo Más probabilidad de superar un fallo transitorio. Más tiempo, más CUs y posibles duplicados. Cuando el error es permanente o la escritura no es idempotente.
Monolito de 100 actividades Todo visible en un canvas. Difícil de probar, versionar y depurar. Cuando aparecen dominios o reutilización: parent/child.
Blast radius

¿Qué rompe si esto falla?

Una tabla bronze suele ser recuperable; una gold que alimenta el cierre contable no. El mismo pipeline no merece el mismo nivel de control en todos los dominios.

Costo

El copy no es gratis

Mover datos consume CUs. Reintentos, archivos pequeños y copias completas innecesarias se acumulan. Mide antes de optimizar; no adivines.

Seguridad

La identidad es parte del diseño

Qué identidad ejecuta el pipeline, a qué conexiones accede y quién puede editarlo. Un pipeline potente con permisos amplios es un riesgo de plataforma.

Observabilidad

Run history no es alerting

Ver el fallo a las 9 a.m. no es lo mismo que enterarte a las 3:10. El Día 20 convierte logs en alertas y runbooks.

★

La pregunta que hace un Staff

“Si este pipeline falla a las 3 a.m., ¿quién se entera, qué ve, qué hace y cómo sabemos que el reintento no empeoró los datos?” Si no puedes responder las cuatro, el pipeline no está terminado.

11

Lente DP-700: lo que el examen quiere ver

El dominio Implement and manage incluye orquestación: elegir pipeline vs notebook, diseñar schedules/triggers y usar parámetros y expresiones dinámicas. Hoy practicas la estructura; el Día 8 añade triggers y patrones metadata-driven.

Pregunta típica

“¿Pipeline o notebook?”

Pipeline para orquestar; notebook para transformar. Si la pregunta describe dependencias, reintentos o copy, piensa pipeline. Si describe joins, ventanas o Spark, piensa notebook.

Pregunta típica

“¿Parámetro o variable?”

Parámetro: valor externo fijo durante el run. Variable: estado interno que puede cambiar. Si el examen dice “se pasa al inicio”, parámetro; si dice “se actualiza durante la ejecución”, variable.

DP

Mini caso de examen

Un pipeline debe ejecutar un notebook solo si la Copy activity copió más de cero filas y, si no, fallar con un mensaje claro. ¿Qué combinación usarías?

Ver respuesta

Copy activity → If Condition sobre @greater(activity('Copy sales').output.rowsCopied, 0) → rama True: notebook; rama False: Fail activity con código y mensaje. La dependencia del notebook es On success del If; el Fail está en la rama False.

Recuerda la regla del curso: si una decisión de producción choca con una respuesta de examen, gana producción y se explica la diferencia. DP-700 valida criterio, no memoria de la UI.

13

Errores frecuentes y anti-patrones

Error 01

Hardcodear fecha y ruta

El pipeline funciona un día y se convierte en deuda al siguiente. Parametriza lo que cambia entre runs.

Error 02

No tener failure path

El fallo se descubre por el dashboard roto. La ruta de fallo contiene y deja contexto; no arregla la causa.

Error 03

Reintentar todo sin pensar

Reintentar un error de permisos o una escritura Append puede duplicar datos y consumir capacidad. Retry solo para transitorios.

Error 04

Poner negocio en expresiones

Una regla de margen escondida en una expresión no se testea ni se versiona. Muévela a notebook o SQL.

Error 05

Append y re-ejecutar

El botón Run se vuelve peligroso. Define write mode y clave; si no, el reintento es una fábrica de duplicados.

Error 06

Confundir run history con observabilidad

Ver el fallo al día siguiente no es operar. Alertas, métricas y runbook llegan en el Día 20.

!

El anti-patrón del canvas gigante

Cien actividades en un solo pipeline no es “control total”; es acoplamiento. Cuando el flujo tiene dominios, reutilización o distintas frecuencias, divide con Invoke pipeline y deja que cada hijo tenga un contrato claro.

Drill de entrevista

i

Pregunta

“Tienes un pipeline que copia ventas a bronze. A las 3 a.m. falla y a las 7 los reportes están vacíos. ¿Cómo lo diseñas para que no vuelva a pasar?”

Respuesta modelo (90 segundos):

  1. Contexto: el copy mueve un archivo por fecha a una tabla bronze; el negocio lo consume a las 7.
  2. Contención: retry acotado para errores transitorios y failure path con un Fail activity que registre archivo, fecha y run ID.
  3. Validación: If Condition que falla si rowsCopied = 0; no declaro éxito por “el copy terminó”.
  4. Re-ejecución: write mode seguro; en el Día 5 sería incremental con merge y clave única, no Append ciego.
  5. Detección: notificación de fallo para runs programados; para algo más rico, monitoring + Activator.
  6. Trade-off: más controles cuestan tiempo y CUs; los aplico según el blast radius de la tabla.
Follow-up 1

¿Retry o volver a ejecutar?

Retry es automático para un fallo transitorio dentro del mismo run. Volver a ejecutar es una decisión operativa posterior; exige idempotencia y evidencia.

Follow-up 2

¿Por qué no lo haces todo en un notebook?

Porque el notebook no te da el mismo control de dependencias, reintentos, parámetros y fallos entre items. Y si lo usas como orquestador, acabas escribiendo un pipeline peor.

English version · 60–90 seconds

“I would treat the pipeline as a control plane, not as the place where business logic lives. The copy activity gets bounded retries for transient failures and a failure path that fails with context: file, date and run ID. On success, an If Condition checks that rows were actually copied; zero rows is a failure, not a success. For reruns, I need a safe write mode; at this stage I would use overwrite for a small batch, and move to incremental merge with a business key in the next session. Finally, I would wire scheduled failure notifications and later add monitoring and alerting. The trade-off is cost and complexity, so I apply stronger controls to tables with larger blast radius.”

15

Cierre: teach-back, cheat sheet y repaso

Teach-back de 2 minutos

Explica en voz alta, sin mirar la lección: “Un pipeline no es un notebook con flechas. Es el plano de control que decide actividades, parámetros, dependencias y qué pasa cuando algo falla. La diferencia entre un run que funciona y uno operable es la evidencia y la contención.”

Si no puedes decirlo en dos minutos, vuelve a las secciones 02, 05 y 06. No sigas al Día 5 con una idea borrosa de qué es una dependencia.

Cheat sheet

  • Pipeline: orquesta; no transforma.
  • Parámetro: entra al run y no cambia; variable: cambia durante el run.
  • Expresión: empieza con @; dentro de texto usa @{...}.
  • Dependencias: success, failure, completion, skip.
  • Retry: transitorios, acotado. Failure path: contexto y contención.
  • Re-ejecución: si no es idempotente, el botón Run es una trampa.
